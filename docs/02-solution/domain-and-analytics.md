# Domain and analytics

Satisfies **REQ-023**, **REQ-028**, **REQ-033**–**REQ-035**, **REQ-039**.

## URLs and DNS

DNS is on Cloudflare. Both hostnames are attached to the Worker as custom domains in `wrangler.toml`, so both resolve to Cloudflare and both are served by the same deployment.

| Item | Current |
|------|---------|
| **`baseURL`** | `https://highlandhideaway.ca/` — the apex |
| **Canonical host** | The apex. Every `<link rel=canonical>`, the sitemap and the Open Graph URLs use it |
| **`www`** | Attached and resolving; **not** redirecting (see below) |

The apex was made canonical on 2026-08-18. See [ADR-0005](adr/0005-make-the-apex-canonical.md). GitHub Pages and the `CNAME` file that pointed at `www` are both gone; DNS finished draining on 2026-08-20.

### The www redirect is missing

`wrangler.toml` and the header comment in `hugo.toml` both describe a Cloudflare Redirect Rule that 301s `www` to the apex. That rule is not deployed. Checked 2026-08-20: `https://www.highlandhideaway.ca/` returns **200** and serves the whole site, as does `https://www.highlandhideaway.ca/posts/welcome/`.

Both files are therefore describing an intention, not the running system. Anyone reading them should not assume the redirect exists.

The impact is limited but real. Canonical tags are correct and absolute on both hostnames, so a `www` page tells search engines the apex is the original, and Google usually consolidates on that. A canonical tag is a hint; a 301 is not. Until the rule exists, `www` URLs can be indexed as duplicates.

Fixing it is dashboard work needing Zone Rules edit permission, which no token in this project holds. Tracked in ISS-27:

> Rules → Redirect Rules. Hostname equals `www.highlandhideaway.ca`, dynamic redirect to `concat('https://highlandhideaway.ca', http.request.uri.path)`, status 301, preserve query string.

The `www` custom domain must stay attached in `wrangler.toml` either way. Removing it stops `www` resolving at all, which takes the redirect down with it.

## SEO surface

- **Titles and descriptions** come from front matter or theme defaults (REQ-033).
- **`robots.txt`** is generated by Hugo (`enableRobotsTXT = true`) and carries the `Sitemap` line. Cloudflare appends its managed content signals to the origin file rather than replacing it, so the served file is the union of both. Before this was set, Hugo emitted nothing and production served only Cloudflare's file, with no `Sitemap` line at all.
- **Sitemap** lists 23 URLs: the pages worth ranking.
- **Taxonomy pages** carry `noindex, follow` and are excluded from the sitemap. Before this change the sitemap advertised 73 URLs, 50 of them auto-generated tag and category pages — navigation outnumbering content two to one. See [ADR-0007](adr/0007-keep-taxonomies-out-of-the-index.md).

Expect roughly 50 URLs under "Excluded by 'noindex' tag" in Search Console once crawling catches up. That is the change working, not a fault.

## Analytics

Three separate things, with different jobs.

### 1. Booking clicks — the conversion signal

Every call to action points at `/go/airbnb` rather than at the listing. `src/worker.js` records the click and 302s onward. This is the site's only conversion signal, because an external listing gives nothing back. See [ADR-0006](adr/0006-count-booking-clicks-in-the-worker.md) and REQ-028.

Rows land in the Analytics Engine dataset `booking_clicks`, bound as `CLICKS`:

| Field | Contents |
|-------|----------|
| index | `"booking"` |
| blob1 | `?src=` — the page the click came from |
| blob2 | referer |
| blob3 | country, from `request.cf` |
| blob4 | `?pos=` — which control: `inline` or `rail` |
| double1 | `1` |

blob4 was appended rather than inserted, deliberately: rows written before the sticky rail existed carry three blobs, and every existing panel reads blob1 to blob3, so adding a field on the end costs no history. Any new CTA placement needs its own `pos` value, or it cannot be told apart from an existing one. ISS-33 covers the mobile placement.

Two properties are worth stating because they are the reason for the design: the count is server-side, so ad blockers cannot suppress it, and no cookie is involved, so it raises no consent question.

Analytics Engine has no UI. The only way to read the dataset is its SQL API, which `grafana/` in this repo provides a local front end for. Retention is three months on the free plan, which bounds the history.

### 2. Page analytics

**Cloudflare Web Analytics**, on automatic injection. Google Analytics is being removed. See [ADR-0008](adr/0008-page-analytics.md) and ISS-28.

Cloudflare injects the beacon at the edge from the automatic setup on the Web Analytics site. It is not in `./public`, and `hugo.toml` sets no beacon of its own — setting `params.analytics.cloudflare.token` would put a second beacon on the page and double-count every view.

Injection only fires for requests that look like a browser. A plain `curl` shows no beacon, and that absence proves nothing:

```bash
curl -s https://highlandhideaway.ca/ -H "User-Agent: Mozilla/5.0 ..." \
  | grep -o "data-cf-beacon='[^']*'"
```

An earlier version of this document said Cloudflare Web Analytics was not enabled. That was wrong, and it came from checking with a plain `curl`. It had been collecting all along, which means the site was briefly running two analytics products at once.

Cloudflare Web Analytics is free and cookieless. It reports page views, referrers, paths and Core Web Vitals, and has no custom events — which costs nothing here, because conversions go through the Worker rather than through any analytics product.

Removing GA closes the consent question in ISS-11 by taking away what raised it, rather than answering it with a banner and a privacy page. Nothing load-bearing goes with it: its unique contribution was session and engagement metrics plus historical continuity, and nothing depends on either. The GA property stops collecting and keeps its history.

**GA is still live.** The removal sits on site repo branch `analytics/cloudflare-web-analytics` (commit `9cd661d`), not merged. `params.analytics.enable` goes to `false` there, since with GA gone the theme has nothing left to render.

The dashboard settings this depends on are listed in `wrangler.toml`, alongside the missing Redirect Rule. Nothing in CI can tell you a dashboard setting was removed, so that list is the only record.

### 3. Edge analytics — always available

Cloudflare's zone-level Analytics and Logs reports requests, bandwidth, cache hit ratio and status codes at the edge. It needs no beacon and is unaffected by the GA decision. It counts requests rather than sessions, so it does not substitute for either product above.
